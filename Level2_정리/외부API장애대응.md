# 🛡️ 외부 API 장애 대응

> **목적**: 네트워크 장애·서버 다운 같은 **환경의 장애가 우리의 장애로 전파되지 않도록** 설계한다.
> **트레이드오프**: 실패의 생애주기 3장 — 결제 시스템이라는 무대에서 경험한 일반 원리들.

## 왜 이 문제가 존재하나

외부 API(토스)를 부르는 순간, 우리의 정상 동작이 **상대의 건강**에 묶인다. 네트워크가 끊기고 상대가 죽으면, 아무 방어가 없으면 그 장애가 우리 스레드·데이터로 그대로 번진다. 이 칸은 그 전파를 막는 설계다. 실패를 **시간 축의 생애주기**로 보면 세 장(章)으로 나뉜다.

## 실패의 생애주기 3장

### 1장 — 모름과 수렴 (실패가 진행 중일 때)
응답을 못 받은 요청은 "실패"가 아니라 **"모름"**이다.
- **멱등키**가 재시도를 안전하게 만든다(같은 요청 두 번 보내도 한 번 처리).
- **조회(reconciliation)**로 확정 상태(성공 or 실패)로 수렴시킨다.
- 타임아웃을 짧게 할수록 원래 성공할 호출까지 끊겨 '모름'·재시도가 늘어 → 멱등키가 더 중요해진다.

### 2장 — 실패의 결말 (실패가 확정될 때)
분리된 세 장치:
- **재시도 한도**: 일시적 실패는 재시도하되 한도를 둔다. 한도를 넘었다는 건 일시적이 아니었다는 뜻(→ permanent 재분류).
- **DEAD 격리**: 한도를 넘은 건은 버리지 않고 자동 처리에서 빼내 사람이 처리한다(DLQ = 폴링 이탈 + 행 보존 + ERROR 알림).
- **보상(Saga)**: 롤백할 수 없는 외부 행동은 반대 행동으로 되돌린다(예: 환불).

### 3장 — 방어벽 (실패가 번지기 전에)
- **Rate Limit**은 호출량(양)을 지켜 평시 quota 약속을 지킨다(토큰 버킷: capacity=순간 버스트, refill=평균 상한 / 인바운드≠아웃바운드).
- **Circuit Breaker**는 건강(실패율 AND 최소 표본)을 재서 죽은 상대를 계속 때리지 않게 스레드를 지킨다.
- 재는 축이 달라 서로를 대신 못 하니 **둘 다** 필요하다.
- 외부 환경 문제로 인한 에러는 **개별 건의 실패 횟수로 세지 않는다**(CB open ↔ DEAD 격리 충돌 해소).

## 관통하는 트레이드오프들

- **스레드 보호 ↔ 모름·재시도**: 타임아웃을 짧게 할수록 '모름'이 늘어 멱등키가 더 중요.
- **fail-fast ↔ 블로킹 대기**: 대기시간 × 동시 대기자 수로 고른다. 그래서 우리 결정은 방향별로 갈렸다 — **인바운드(손님 요청)는 fail-fast로 즉시 거절**(429 + Retry-After: 무계 손님이라 붙잡으면 대기자만 쌓임), **아웃바운드(토스 호출 워커)는 bounded wait로 붙잡되 마감을 건다**(`tryConsume(Duration maxWait)` 2s, 유계 워커라 잠깐 기다리는 게 이득, 넘기면 거절 폴백).
- **양 ↔ 건강**: Rate Limit은 양을, Circuit Breaker는 건강을 잰다.
