# 🧪 테스트

> **목적**: 테스트는 **변경을 가능하게 한다** — 기능 명세서처럼 각 층의 책임이 무엇을 보장해야 하는지 드러내고, 책임이 명시되기에 변경이 가능해진다.
> **트레이드오프**: ① 격리 ↔ 실제성 · ② 검증하려는 책임이 테스트 단위를 나눈다.

## 왜 이 문제가 존재하나

코드를 바꾸고도 "안 깨졌다"를 확신하려면 근거가 필요하다. 테스트는 **기능 명세서**처럼, 내가 무엇을 신경 써서 코딩했는지를 드러낸다 — Domain은 Domain이 지키는 규칙을, Service는 흐름과 외부 경계를 보여준다. 그래서 테스트의 목적은 단순히 "버그 잡기"가 아니라 **각 층의 책임을 명시하는 것**이고, 책임이 명시되기에 변경이 가능해진다.

## 트레이드오프 ① — 격리 ↔ 실제성

검증 대상이 "진짜"를 요구하는 만큼만 무겁게 간다.
- 가벼운 mock/단위 = 빠르고 격리됨, 그러나 실제 동작과 멀어질 수 있음.
- 무거운 실제 엔진 = 느리지만 진짜를 본다.
- **진짜 경합·락 사고(데드락)는 진짜 엔진 위에서만 보인다** — H2로는 안 나오던 gap 락 데드락이 Testcontainers MySQL에서 드러났다(#56).

## 트레이드오프 ② — 책임이 테스트 단위를 나눈다

테스트 단위를 나누는 1차 기준은 **각 층이 든 책임**이다.
- **Domain**: 외부 경계가 거의 없고 검증 같은 비즈니스 규칙만 → **작고 빠른 단위 테스트**가 쉽다.
- **Service**: DB·트랜잭션·락·Repository와 엮인다 → **통합 테스트의 이점이 크다**(`@JdbcTest` 등). 쿼리만 보는 Repository 단위 테스트보다, 서비스 흐름·트랜잭션 경계·락·저장 결과까지 같이 검증하는 게 낫다.
- **Controller**: **API 계약**(status·JSON·validation·인증/인가·예외 응답)을 볼지, 사용자 관점 전체 흐름을 볼지에 따라 **슬라이스(`@WebMvcTest`) vs 인수 테스트**를 고른다.

## 실패 모드 — 초록이어도 신뢰를 못 주는 테스트

검증하려는 **책임을 잊고** mock 호출 횟수·메서드 호출 여부·커버리지 숫자만 확인하면, 초록색이어도 안심을 못 준다. 진짜 질문(중복 대기가 막혔나 / 5명 초과가 불가능한가 / 동시 요청에도 최종 상태가 안전한가 / HTTP 응답 계약이 지켜지나)에 답하지 않고 **구현 방식만 고정하고 책임은 검증하지 못한다.** → **호출을 세지 말고 책임(불변식·계약)을 검증하라.**

## 다른 칸으로 잇는 다리

- **[🧩 모델링](복잡한모델링.md)**: 책임을 잘 나누면 테스트도 작고 선명해진다. 책임이 섞이면 테스트도 커지고 느려지고, 무엇이 깨졌는지 알기 어렵다.
- **[🗄️ DB·트랜잭션](DB트랜잭션.md)**: Service 테스트에 DB·트랜잭션·락이 끼면 테스트는 DB 칸으로 이어진다. 본질은 "락 메서드가 호출됐는가"가 아니라 **"동시성 속에서도 최종 불변식이 깨지지 않는가"** — 실패 모드와 같은 경계다(#56이 그 "진짜"를 Testcontainers로 본 사례).
