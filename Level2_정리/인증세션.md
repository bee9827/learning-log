# 🔑 인증·세션

> **목적**: HTTP는 무상태라, 클라이언트는 매 요청마다 신원을 증명할 증표를 전달해야 한다 (세션 = JSESSIONID / 토큰 = JWT).
> **트레이드오프**: 상태를 서버에 저장하면 무효화가 편하고, 안 하면 확장이 편하다.

## 왜 이 문제가 존재하나

HTTP는 stateless — 매 요청이 독립이고, 서버는 요청 사이에 아무것도 기억하지 않는다 (확장성·단순성 때문). 그런데 로그인은 "이 사람 인증됨"이라는 **상태를 얹는** 일이다. 그 상태를 **어디 두느냐**가 이 카테고리 전체를 가른다.

로그인은 처음 한 번만 id/password로 하고, 그 뒤 매 요청엔 "나 아까 그 사람"을 증명할 **증표**를 실어 보낸다.

## 선택지

**세션 — 서버가 보관 (stateful)**
- 로그인 검증 → 서버가 유저 상태를 세션에 저장 + **JSESSIONID**(의미 없는 난수 = 참조 열쇠) 발급 → 쿠키로 전달.
- 이후 매 요청에 JSESSIONID 자동 첨부 → 서버가 ID로 금고를 조회.
- JSESSIONID는 내용물이 아니라 **열쇠**라서 "나 admin"으로 위조할 수 없다. (열쇠를 훔치는 세션 하이재킹은 별개 문제.)

**토큰 — JWT, 클라이언트가 보관 (stateless)**
- 구조: **Header**(알고리즘) . **Payload**(권한 등 실제 정보) . **Signature**(무결성 검증).
- Payload는 암호화가 아니라 **Base64 인코딩** — 누구나 열어 읽는다(jwt.io). JWT가 지키는 건 기밀성이 아니라 **무결성**(위조 방지).
- Signature = `(Header.Payload)` + **서버만 아는 secret**으로 계산한 값. 검증 = 받은 내용으로 재계산 후 비교. 공격자는 secret이 없어 유효한 서명을 못 만든다 → 위조는 즉시 들통.
- payoff: 서버는 secret 하나로 어떤 토큰이든 검증 → 유저별 상태 저장 불필요 = **stateless**.

## 트레이드오프

- 축 = **상태를 어디 두나** (서버 vs 클라이언트).
- **세션**: 무효화 쉬움(서버에서 지우면 즉시 차단) ↔ 확장 어려움(서버 여러 대면 세션 공유 필요).
- **JWT**: 확장 쉬움(secret만 있으면 됨) ↔ 무효화 어려움(발급된 토큰은 만료까지 유효).
- **탈취 관점 정정**: 세션·JWT 둘 다 헤더에 실려 다녀 훔치는 난이도는 비슷하다. 다른 건 **훔친 뒤의 회수 가능성** — 세션은 지워서 죽이고, JWT는 만료까지 못 죽인다.

## 절충 — 하이브리드

- **짧은 만료 JWT**(빈번한 API 요청 = stateless 검증 길) + **refresh token**(드문 재발급 길).
- refresh token은 **세션 세계의 물건** — 서버(DB)에 저장해 비교·갱신하므로, 탈취돼도 지워서 죽일 수 있다.
- JWT 만료를 "짧게" 잡는 다이얼 = **탈취당했을 때 물릴 수 있는 최대 피해 시간**. 짧을수록 안전하지만 재발급(stateful 길)을 자주 탄다.
- → 1부 DB 칸의 **낙관 + 비관 락 혼합**과 같은 모양: 양쪽을 동시에 못 가지니 두 세계를 섞는다.
