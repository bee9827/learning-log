# 💳 외부 결제 연동

> **목적**: 클라이언트도 외부도 믿지 않는다 — **돈의 정확성은 서버가 쥔다.**
> **트레이드오프(코어)**: 인증 vs 승인 · 금액 검증 · 주문 상태 기계.

## 왜 이 문제가 존재하나

결제는 돈이라, 틀리면 곧바로 사고다. 그래서 두 방향을 다 불신한다:
- **클라이언트**가 보낸 값(금액 등)은 위조 가능 → 그대로 믿지 않는다.
- **외부(토스)** 응답도 그대로 신뢰하지 않고 서버가 진실을 쥔다.

이 칸은 **정상 세계의 필수**(코어)만 다룬다. 실패가 존재하는 세계(timeout·재시도·보상·차단)는 [🛡️ 외부 API 장애 대응](외부API장애대응.md)으로 분리했다.

## 코어 3요소

**1. 인증 vs 승인 (다른 단계)**
- 사용자가 결제창에서 결제수단을 확인하는 **인증**과, 서버가 실제 매출을 일으키는 **승인(confirm)**은 다른 단계다.
- 인증만으로는 돈이 오간 게 아니다 → 서버의 confirm이 진짜 결제.

**2. 금액 검증 (서버 저장값과 대조)**
- 클라이언트가 보낸 금액을 믿지 않고, **주문 시점에 서버가 확정해 저장한 금액**과 대조한다.
- "클라이언트 값은 위조 가능"이라는 인증 칸의 뼈대와 같다 — 서버 secret·진짜 값으로 검증.

**3. 주문 상태 기계 (확정 안 된 상태 포함)**
- 주문을 PENDING 등 **확정되지 않은 상태를 포함한 상태 기계**로 관리한다.
- 결제 시작 시점에 주문을 생성하고, 중복 주문은 **3중 방어**로 막는다: getOrCreate + 멱등 취소 + `UNIQUE(reservation_id)` 백스톱.

## DB 칸과의 연결

- **금액·상태의 정확성**은 결국 [🗄️ DB·트랜잭션](DB트랜잭션.md)의 도구로 지켜진다 — 중복 주문 방지에 UNIQUE 제약이 그대로 재등장(#43).
- 멱등키는 여기서 "반쪽"만 등장하고(#53), 온전한 멱등·재시도는 장애 대응 칸에서 완성된다.
