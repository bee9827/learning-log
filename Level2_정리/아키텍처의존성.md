# 🏗️ 아키텍처·의존성

> **목적**: 무엇이 무엇을 알게 할지(의존 방향)와 경계를 정한다 — 변경이 한 곳에 갇혀 번지지 않도록.
> **트레이드오프/원리**: 순환참조를 끊는 방법은 "즉시 필요한가"로 갈리고, 한 트랜잭션에 묶을지 뗄지는 강한 일관성과 최종 일관성 사이의 선택이다.

## 왜 이 문제가 존재하나

기능을 기능별 패키지로 나누자, **서로가 서로를 아는 순환참조**가 생기기 쉬운 구조가 드러났다. 순환참조는 스프링 기동 실패로도 이어지고, "이 로직이 왜 여기 있지?" 같은 **책임 오배치**의 증상이기도 하다. 이 카테고리는 결국 하나의 질문에 답한다:

> **누가 누구를 알 수 있는가?** — 그 방향과 경계를 정해서, 한쪽이 바뀌어도 변경이 번지지 않게 한다.

## 1. 순환참조를 끊는 방법은 "즉시 필요한가?"로 갈린다

같은 순환참조라도 끊는 도구가 달랐다. 기준은 **그 일이 즉시 일어나야 하는가**였다.

- **결제 → 예약 (즉시 필요)**: 결제되면 예약이 **즉시** 확정돼야 한다(손님이 화면 앞에서 기다리니까). 그래서 **주문(Order)을 결제 시작 시점에 미리 만들어** 결제 유실에 대비했는데 — 이 Order가 예약도 결제도 모르는 **중립 지대**라, 예약↔결제가 서로 직접 부르던 순환도 **덤으로** 풀렸다. (Order의 일차 목적은 유실 방지, 사이클 끊기는 그 구조가 준 부수 효과.)
- **예약취소 → 대기 승격 (나중에 해도 됨)**: 취소 뒤 다음 대기자 승격은 즉시가 아니어도 괜찮다. 그래서 취소할 때 **"승격해야 함"이라는 메모만 남기고**, 별도 일꾼(워커)이 나중에 처리한다.

## 2. 한 묶음으로 처리할까, 떼어낼까 (원자성을 어디서 끊나)

- A의 예약취소와 B의 대기승격을 **한 묶음(한 트랜잭션)**으로 처리하면, B 승격이 실패할 때 **A의 취소까지 막힌다**. A의 정당한 취소가 남의 장애로 불발되면 안 된다.
- 그래서 **떼어냈다** — 취소는 바로 끝내고, 승격은 메모 + 일꾼에게 맡긴다(아웃박스 패턴). 강한 일관성을 **최종 일관성**으로 내린 것.
- **대가**: 공짜가 아니었다. 관리할 게 늘었다 — 같은 메모를 두 번 처리하지 않기(멱등성), 동시 처리 충돌(동시성), "대기자는 있는데 자리는 아직 빈" 순간의 예외 처리. `Promotion` 도메인과 워커가 이때 생겼다.
- ※ 이 "묶기 vs 떼기"는 [🗄️ DB·트랜잭션](DB트랜잭션.md)의 **원자성(A)**과, [🛡️ 외부 API 장애 대응](외부API장애대응.md)의 **아웃박스·멱등성**과 같은 뿌리다.

## 3. ACL — 외부를 우리 안에 들이지 않는다

- 토스 같은 외부 API 타입은 **어댑터(포트) 안에 가둔다**. 경계에서 우리 타입으로 **번역해서** 받고, 외부 타입은 그 밖으로 **못 나간다**.
- 막으려는 "부패(corruption)" = **우리 도메인이 외부 세계의 모양에 오염되는 것.**
- 효과: 토스가 응답 구조를 바꾸면 **어댑터 한 곳만** 고치면 되고, 결제사를 갈아타면 **포트 뒤 구현만** 교체하면 된다.

## 4. 규칙을 사람이 매번 못 지키니 자동으로 검사한다

- "누가 누구를 알아도 되는가"라는 규칙(순환 금지·ACL 경계)은 사람이 매번 기억해 지키기 어렵다.
- 코드가 서로를 **import하는지 자동 검사**해서 규칙 위반을 막는 방법이 있다(ArchUnit). — 개념만 확인했고 직접 구현은 아직 안 함.
