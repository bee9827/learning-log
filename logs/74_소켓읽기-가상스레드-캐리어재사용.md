## 출발점 — 왜 병렬 Stream에는 가상 스레드를 쓰지 않을까

병렬 Stream은 CPU 계산을 여러 덩어리로 나누는 작업이다. 가상 스레드는 CPU 코어를 늘리거나 계산을 빠르게 하지 않는다. 많은 작업이 네트워크 응답을 기다릴 때 플랫폼 스레드가 그 요청에 계속 묶이지 않게 해 동시 처리량을 늘린다. 가상 스레드가 계산하는 동안에는 결국 캐리어 플랫폼 스레드가 필요하다. 병렬 Stream의 공용 ForkJoinPool과 가상 스레드 스케줄러의 ForkJoinPool은 서로 다르다. [JEP 444](https://openjdk.org/jeps/444)

## 요청 A의 생애주기

~~~text
A가 캐리어 P1에 mount → A의 Java 코드 실행
→ A가 소켓 read 호출, 아직 읽을 바이트 없음
→ JDK가 A를 중단하고 실행 위치·호출 스택을 보관, P1을 해제
→ P1은 다른 가상 스레드 B를 실행
→ 원격 상대가 데이터를 보냄, OS가 소켓에서 수신
→ JDK의 I/O 처리가 A를 실행 가능 상태로 만들어 스케줄러에 제출
→ 빈 캐리어 P1 또는 P2에 A가 mount, read를 이어서 실행
~~~

플랫폼 스레드가 가상 스레드의 코드를 실제 CPU에서 실행해 주기 때문에 **캐리어**라고 부른다. 가상 스레드는 실행 중에는 캐리어가 필요하지만 대기 중에는 캐리어 없이 존재한다. 호출 스택은 Java 힙의 stack chunk에 보관될 수 있다. 원래 캐리어에 돌아가야 하는 것은 아니며, 소켓이 직접 스케줄러를 호출하는 것도 아니다. OS가 소켓 상태를 관리하고 JDK가 완료 준비를 전달한다. [JEP 444](https://openjdk.org/jeps/444)

플랫폼 스레드가 소켓 응답을 기다려도 CPU를 계속 쓰는 것은 아니다. 다만 그 스레드 자체가 대기 중인 요청에 묶인다. 많은 요청이 이 상태가 되면 처리용 스레드 풀이 고갈되어 새 요청이 대기하거나 제한 시간에 걸릴 수 있다. 가상 스레드는 지원되는 블로킹 I/O에서 캐리어를 놓는다. 모든 블로킹 작업이 반드시 언마운트되는 것은 아니다.

## 변호사·사건 서류·비서 비유

변호사는 플랫폼 스레드(캐리어)다. 사건 서류는 가상 스레드에 해당한다. 서류에는 지금까지 처리한 내용뿐 아니라 다음에 이어서 처리할 지점이 담긴다. 단순한 기록지가 아니라 멈췄다가 다시 실행될 수 있는 **사건 자체**로 생각해야 한다. 비서는 JVM 스케줄러로, 실행 가능한 사건을 사용 가능한 변호사에게 배정한다.

~~~text
변호사가 사건 A를 처리하다 의뢰인의 자료를 기다림
→ 사건 A의 진행 상태는 가상 스레드에 남고, 변호사는 사건 B를 처리함
→ 자료가 소켓으로 도착하면 OS의 수신 정보를 JDK가 확인함
→ JDK가 사건 A를 다시 실행 가능한 상태로 만들어 스케줄러에 제출함
→ 사용 가능한 변호사가 사건 A의 중단 지점부터 이어서 처리함
~~~

변호사가 새 사건을 기다리며 상시 근무하는 모습과, **진행 중인 사건의 자료를 기다리는 모습**은 다르다. 가상 스레드가 캐리어를 놓는 것은 후자의 대기다. 사용자가 보내는 요청 데이터뿐 아니라 DB나 외부 API의 응답을 기다릴 때도 같은 원리가 적용된다. 비서는 사건의 우선순위를 꼭 정한다기보다 실행 가능한 사건을 배정한다.

## 소켓이 연결되어 있어도 언제 read가 멈추는가

연결 상태와 지금 읽을 바이트가 있는지는 다르다. InputStream.read()는 데이터, 스트림 종료, 오류 중 하나가 나타날 때까지 기다릴 수 있다. read(byte[])는 최대 버퍼 크기만큼 읽되 일부만 반환할 수 있다. readNBytes(n)는 n바이트, 종료, 오류 중 하나가 발생할 때까지 기다린다. [InputStream API](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/io/InputStream.html)

예를 들어 애플리케이션 메시지가 10바이트인데 3바이트만 도착했다면, 일반 read는 3바이트를 반환할 수 있다. 애플리케이션이 나머지 7바이트를 읽으려고 다시 호출하면 또 대기한다. readNBytes(10)은 호출 내부에서 부족한 바이트를 기다릴 수 있다. 가상 스레드는 데이터가 없는 대기 구간마다 언마운트됐다가 다시 실행될 수 있다.

TCP는 바이트 스트림이므로 송신자가 한 번 쓴 단위와 수신자의 한 번의 read 결과가 맞아떨어진다는 보장이 없다. 메시지 길이·구분자·종료 조건은 애플리케이션 프로토콜이 정한다. 큰 메시지는 여러 번 읽고, 반대로 작은 바이트가 여러 번 도착해도 완성 조건을 채울 때까지 기다릴 수 있다. [RFC 9293](https://www.rfc-editor.org/rfc/rfc9293.html)

읽기 제한 시간은 Socket.setSoTimeout(ms)이다. 시간이 만료되면 SocketTimeoutException이 발생하나 소켓은 유효하며, 0은 무한 대기 설정이다. 연결을 맺는 connect timeout과 구분한다. [Socket API](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/net/Socket.html)

## 한 문장 봉인

> 가상 스레드는 코드를 실행할 때 캐리어가 필요하지만 소켓 데이터가 없는 동안에는 실행 상태를 보관하고 캐리어를 놓는다. OS가 데이터를 받으면 JDK가 가상 스레드를 다시 스케줄러에 제출하고, 어느 사용 가능한 캐리어에서든 읽기를 이어 간다.

## 학습 방식 회고

- 처음부터 “mount/unmount”와 CPU/I/O 용도를 말했을 때 전체 그림이 잡히지 않았다. 요청 A·B와 캐리어 하나의 시간선을 그린 뒤에야 학습자가 “OS가 소켓을 관리하므로 가능한 방식”이라고 스스로 연결했다.
- 학습자가 직접 정리한 문장에서 “JVM이 블록되지 않는다”는 말은 “가상 스레드는 중단되지만 캐리어는 묶이지 않는다”로, “소켓이 스케줄러에 올린다”는 말은 “OS 수신 → JDK I/O 처리 → 스케줄러 제출”로 다듬었다. 다음에도 용어보다 사건 순서를 먼저 제시한다.
- 소켓 read가 버퍼를 항상 꽉 채울 것이라는 가설은 read와 readNBytes의 반환 조건을 비교하며 정리됐다. 이때 앞선 로그 #72의 ‘호출한 쪽은 어디서 기다리는가’가 실제 네트워크 읽기에 연결됐다.

## 재방문 질문과 다음 씨앗

- 연결은 살아 있지만 읽을 바이트가 없을 때 가상 스레드와 캐리어는 각각 어떤 상태인가?
- 10바이트 중 3바이트만 도착했을 때 read(byte[])와 readNBytes(10)의 완료 조건은 어떻게 다른가?
- 다음 씨앗: OS의 소켓 준비 이벤트를 JDK가 받는 구체적 경로와, 언마운트되지 않는 블로킹·pinning. 현재 BACKLOG의 hot arc는 컴퓨터 구조 순회이므로 새 항목은 추가하지 않는다.
