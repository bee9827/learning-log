## CPU 안의 책임 분리

처음에는 “레지스터에 값을 두고 명령어를 기반으로 CPU가 계산한다”는 설명에서 출발했다. CPU 내부 역할을 나누면 다음과 같다.

```text
레지스터 → 명령어·주소·데이터·중간 결과를 기억
제어장치 → 명령어를 해독하고 클록에 맞춰 제어 신호 전송
ALU      → 산술·논리 연산 수행
```

`EAX·EBX·ECX`, 스택 포인터, 프로그램 카운터와 상태 레지스터는 소프트웨어에 드러나는 아키텍처 레지스터다. 반면 MAR·MBR·IR은 메모리 접근과 명령어 처리의 역할을 설명하는 기본 모형이다. 현대 CPU에서는 이 역할이 파이프라인 레지스터, 명령어 큐, 로드·스토어 유닛과 여러 내부 버퍼로 나뉠 수 있다.

## PC에서 실행까지 — 명령어 인출·해독·실행

PC(Program Counter)는 다음에 가져올 명령어 주소를 가진다. x86-64에서 같은 역할을 하는 실제 레지스터 이름은 RIP다.

```text
PC  → 다음 명령어 주소
MAR → 지금 메모리에 요청할 주소
MBR → 메모리와 주고받는 내용
IR  → 현재 해석·실행할 명령어
```

기본 인출 사이클은 다음처럼 이어진다.

```text
MAR ← PC
MBR ← Memory[MAR]
IR  ← MBR
PC  ← 다음 명령어 주소
```

IR은 기계어를 연산으로 바꾸는 주체가 아니라 현재 명령어 비트를 보관한다. 제어장치의 디코더가 IR을 해석하고, 레지스터와 ALU 등에 제어 신호를 보내 실행한다.

```text
PC → MAR → RAM → MBR → IR
                       ↓
                 제어장치가 해독
                       ↓
             레지스터 → ALU → 결과 저장
```

## 피연산자의 의미는 이미 인코딩되어 있다

처음에는 `100`이 MAR·MBR·IR 중 어디에 있느냐에 따라 주소·레지스터·값으로 해석된다고 생각했다. 실제로는 어셈블러가 opcode와 주소 지정 방식 등을 포함한 **전체 명령어 인코딩**에 그 의미를 미리 기록한다.

```text
[ADD][즉시값 방식][100]   → 숫자 100을 사용
[ADD][레지스터 방식][R1]  → R1 값을 사용
[ADD][메모리 방식][100]   → 메모리 주소 100의 값을 사용
```

모든 명령어는 먼저 인출·해독된다. 이후 피연산자를 어디서 가져오는지가 갈린다.

```text
즉시값   → 명령어 안의 값을 바로 ALU에 전달
레지스터 → 지정된 범용 레지스터 값을 ALU에 전달
메모리   → MAR에 데이터 주소를 넣고 MBR로 읽은 뒤 ALU에 전달
```

`0x`는 주소 표시가 아니라 16진수 표기다. 즉시값도 `0x1000`으로 쓸 수 있다. `#` 역시 모든 어셈블리의 공통 문법이 아니라 ARM 계열에서 즉시값을 표시하는 문법이다. x86 Intel 문법에서는 `mov eax, 100`처럼 쓰고 메모리 참조를 `[100]`처럼 구분한다.

## 호출과 인터럽트가 PC를 바꾸는 방법

일반 명령어에서는 PC가 다음 주소로 진행하지만, 분기와 함수 호출은 목적지 주소로 PC를 바꾼다. 함수 호출은 함수가 끝난 뒤 이어갈 **복귀 주소**를 스택이나 링크 레지스터 등에 보존한다.

여기서는 키보드·네트워크 장치처럼 **외부 하드웨어 인터럽트의 기본 모형**만 다룬다. 프로그램의 `call` 명령이 아니라 외부 사건에서 실행 흐름이 바뀐다.

```text
인터럽트 도착
→ 현재 명령어를 안전한 경계까지 완료
→ 다음에 돌아올 PC와 CPU 상태 저장
→ 인터럽트 번호로 벡터 테이블 조회
→ 핸들러 주소를 PC에 설정
→ 핸들러 실행
→ 저장한 상태와 PC 복원
```

인터럽트 번호는 “어떤 처리 코드를 실행할까”를 찾는 식별자다. 파일 디스크립터는 프로세스별 테이블에서 열린 파일·소켓 같은 I/O 자원을 찾는 식별자이므로 목적과 범위가 다르다.

동기 예외·fault는 문제 명령어를 다시 실행하기 위해 저장하는 주소가 달라질 수 있으므로 이번 노드에서는 섞지 않고 후속 씨앗으로 남긴다.

## 대화에서 합의한 최종 흐름

학습자가 작성한 흐름에 대화에서 확인한 교정을 반영해 다음처럼 합의했다.

PC가 다음 명령어 주소를 가지고 있고, 그 주소를 MAR로 옮겨 RAM에서 명령어를 읽어 MBR과 IR로 전달한다. 제어장치의 디코더가 명령어를 해석하고 클록에 맞춰 제어 신호를 보내며, 필요한 값은 주소 지정 방식에 따라 명령어·레지스터·메모리에서 가져와 ALU가 연산한다. 외부 하드웨어 인터럽트가 오면 현재 명령어를 마친 뒤 복귀할 PC와 실행 상태를 저장하고, 인터럽트 벡터 테이블에서 핸들러 주소를 찾아 실행한 다음 원래 상태로 복귀한다.

## 처음 설명에서 바뀐 점

- IR이 연산으로 변환하는 것이 아니라 제어장치가 IR을 해독한다고 역할을 분리했다.
- 명령어 인출과 피연산자 인출을 같은 과정으로 보던 설명을 나눴다.
- 같은 숫자의 의미는 임시 레지스터의 위치가 아니라 완성된 명령어 인코딩으로 결정된다고 교정했다.
- 인터럽트 번호가 직접 연산을 뜻하는 것이 아니라 벡터 테이블에서 핸들러 주소를 찾는 열쇠라고 구체화했다.
