## 출발점 — SSD의 프로그램이 CPU에서 실행되기까지

처음 알고 있던 것은 RAM이 SSD보다 빠르고 비싸며 휘발성이라는 점이었다. 프로그램 실행 흐름을 다음처럼 연결했다.

```text
SSD에 저장된 실행 파일
→ 기계 명령어와 필요한 데이터가 RAM에 올라감
→ CPU가 기계 명령어를 읽고 연산
→ 영속적으로 남겨야 하는 결과는 SSD에 저장
```

여기서 `프로그램을 RAM에 올리는 주체`와 `명령을 실행하는 주체`가 섞였다. 운영체제도 결국 CPU가 실행하는 기계 명령어이지만 책임은 구분된다.

```text
운영체제 → 프로세스와 메모리 자원을 만들고 관리
CPU      → 운영체제와 사용자 프로그램의 기계 명령어를 실행
```

## 왜 프로세스의 메모리를 격리해야 하나

여러 프로그램이 같은 RAM 주소를 아무 구분 없이 사용하면 한 프로그램이 다른 프로그램의 값을 덮어쓸 수 있다. 더 위험한 경우는 덮어쓴 값이 당장 오류처럼 보이지 않아 전혀 다른 위치에서 뒤늦게 문제가 터지는 것이다.

따라서 각 프로세스에는 자기만의 메모리를 쓰는 것처럼 보이는 **가상 주소 공간**이 필요하다.

처음에는 프로세스 B의 모든 주소에 일정한 값 `x`를 더하는 베이스 방식이 떠올랐다.

```text
B의 물리주소 = B 전용 베이스 + 논리주소
```

이 방식은 프로세스 전체가 연속된 물리 메모리에 들어갈 때는 동작한다. 그러나 남은 RAM이 여러 곳으로 흩어져 있으면 충분한 총공간이 있어도 하나의 연속 공간을 찾지 못한다. 프로세스를 LinkedList처럼 흩어진 공간에 놓고 연속처럼 보이게 하자는 생각에서, 일정한 크기의 조각과 그 대응 관계를 관리하는 구조로 발전했다.

## 페이지와 프레임

- **페이지(page)**: 가상 주소 공간을 나눈 고정 크기 조각
- **프레임(frame)**: 물리 메모리를 같은 크기로 나눈 조각
- **페이지 테이블(page table)**: 각 가상 페이지가 어느 물리 프레임에 연결되는지 기록

가상주소는 `가상 페이지 번호 + 페이지 내부 오프셋`으로 나뉜다. 페이지를 다른 프레임으로 옮겨도 페이지 내부 위치는 변하지 않으므로 오프셋은 그대로 유지된다.

페이지 크기가 4KB일 때 가상주소 10KB는 다음과 같다.

```text
10KB = 가상 페이지 2 + 오프셋 2KB
```

가상 페이지 2가 물리 프레임 7에 연결되어 있다면:

```text
물리주소 = 7 × 4KB + 2KB = 30KB
```

`프레임 7`은 주소가 아니라 0부터 세는 **프레임 번호**다. 따라서 프레임 7의 시작 주소가 `7 × 4KB = 28KB`가 된다.

## MMU — 운영체제가 만든 규칙을 매 접근에 적용하는 하드웨어

MMU(Memory Management Unit)는 현대 CPU 내부에서 가상주소를 물리주소로 변환하고 접근 권한을 검사하는 하드웨어다.

```text
CPU가 가상주소로 읽기·쓰기 요청
→ MMU가 페이지 번호와 오프셋 분리
→ 페이지 번호를 물리 프레임 번호로 변환
→ 프레임 번호 + 오프셋으로 물리주소 완성
→ load/store라면 CPU 데이터 캐시 확인
→ 데이터 캐시에도 없으면 RAM 접근
```

운영체제는 페이지 테이블과 권한을 만들고, MMU는 CPU의 모든 메모리 접근에서 그 규칙을 빠르게 집행한다.

## TLB — 실제 데이터가 아니라 주소 번역 결과의 캐시

페이지 테이블도 메모리에 있으므로 실제 데이터를 한 번 읽기 위해 페이지 테이블과 데이터 메모리를 연속해서 조회하면 비용이 커진다. 이때 캐시 전략이 다시 등장한다.

TLB(Translation Lookaside Buffer)는 MMU 가까이에 있는 주소 번역 전용 캐시다.

```text
TLB가 저장하는 것  → 가상 페이지 번호 → 물리 프레임 번호, 접근 권한
CPU 캐시가 저장하는 것 → 실제 명령어나 데이터(I-cache·D-cache, 또는 통합 캐시)
```

```text
TLB 적중 → 이미 저장된 번역을 사용
TLB 실패 → 페이지 테이블을 조회한 뒤 번역 결과를 TLB에 저장
```

## 같은 가상주소가 프로세스마다 다른 이유

가상주소는 컴퓨터 전체에서 유일한 숫자가 아니다. 각 프로세스의 **주소 공간 안에서만** 의미가 있다. 같은 프로그램을 두 번 실행해도 서로 다른 프로세스이므로 같은 가상주소가 서로 다른 물리 프레임을 가리킬 수 있다.

```text
프로세스 A: 가상 페이지 2 → 물리 프레임 7
프로세스 B: 가상 페이지 2 → 물리 프레임 12
```

주소 변환의 입력은 사실상 다음 두 값이다.

```text
현재 프로세스의 주소 공간 + 가상주소
```

TLB도 이를 구분해야 한다. 프로세스 전환 시 이전 TLB 기록을 비우거나, ASID/PCID 같은 주소 공간 식별자를 번역 기록과 함께 사용한다.

```text
(주소 공간 A, 가상 페이지 2) → 물리 프레임 7
(주소 공간 B, 가상 페이지 2) → 물리 프레임 12
```

처음 생각했던 `프로세스마다 +x` 방식과 페이지 오프셋은 다른 개념이었다. 페이징에서도 베이스와 오프셋 사고는 남지만, 프로세스 전체에 베이스 하나를 더하는 대신 **각 페이지가 연결된 물리 프레임의 시작점에 페이지 내부 오프셋을 더한다.**

## 프로세스 격리와 물리 페이지 공유는 동시에 가능하다

프로세스가 다르다고 모든 물리 메모리를 두 벌로 복제할 필요는 없다. 같은 프로그램의 읽기 전용 기계어처럼 변경되지 않는 데이터는 두 프로세스의 페이지 테이블이 같은 물리 프레임을 가리키게 할 수 있다.

```text
A의 코드 페이지 5 ─┐
                    ├→ 물리 프레임 20 (읽기·실행, 쓰기 금지)
B의 코드 페이지 5 ─┘
```

스택이나 힙처럼 각 프로세스에서 달라져야 하는 영역은 서로 다른 프레임에 연결한다. 격리는 `모든 물리 메모리를 복제하는 것`이 아니라 **페이지별 매핑과 권한을 다르게 구성하는 것**이다.

## Copy-on-Write — 실제 쓰기가 발생한 페이지 하나만 분리

수정 가능한 데이터도 처음부터 모두 복사하면 대부분 읽기만 하는 상황에서 낭비다. 그래서 처음에는 물리 프레임을 공유하고 쓰기 금지로 표시한 뒤, 실제 쓰기가 발생한 페이지 하나만 복사한다. 이것이 Copy-on-Write(COW)다.

```text
A와 B가 같은 물리 프레임을 COW 상태로 공유
→ A가 쓰기 시도
→ MMU가 PTE의 쓰기 금지 권한을 보고 예외 발생
→ 운영체제가 새 물리 프레임 확보
→ 기존 페이지 전체를 새 프레임으로 복사
→ A의 해당 PTE만 새 프레임을 가리키도록 변경하고 쓰기 허용
→ A의 낡은 TLB 항목 무효화
→ 중단됐던 쓰기 명령 재실행
```

**PTE는 Page Table Entry**다. 가상 페이지 하나의 물리 프레임 번호와 접근 권한 등을 담는 페이지 테이블의 항목이다. COW가 발생할 때 페이지 테이블 전체를 새로 만드는 것이 아니라 쓰기가 발생한 가상 페이지의 PTE를 바꾼다.

MMU가 COW 정책을 이해하는 것은 아니다. 하드웨어인 MMU는 PTE와 TLB에 캐싱된 권한을 보고 쓰기를 막고 예외를 발생시킨다. 운영체제가 그 예외를 받아 진짜 읽기 전용 페이지인지 COW 페이지인지 판단한다.

```text
하드웨어가 제공하는 것 → 읽기(R)·쓰기(W)·실행(X) 같은 접근 권한과 예외
운영체제가 구현하는 것 → 그 권한과 예외를 이용한 COW 정책
```

## 페이지 크기는 두 비용 사이의 저울이다

4KB 페이지에서 1바이트만 수정해도 운영체제는 그 바이트의 의미를 모르므로 COW 시 물리 프레임 4KB 전체를 복사한다. 페이지를 작게 만들면 COW 복사 낭비와 내부 단편화는 줄일 수 있지만, 같은 주소 범위를 표현하는 페이지와 PTE 개수는 늘어난다.

```text
16KB 주소 범위
4KB 페이지 → 페이지 4개, PTE 4개
1KB 페이지 → 페이지 16개, PTE 16개
```

여기서 페이지의 **용량**과 프로그램의 **실제 사용률**을 구분해야 한다. 4KB 페이지의 4096바이트는 모두 주소로 사용할 수 있고 PTE 같은 관리 정보는 별도 페이지 테이블에 있다. 다만 프로그램이 모든 바이트를 실제로 사용하지 않으면 내부 단편화가 생긴다.

```text
큰 페이지 → PTE 수와 관리 비용 감소 / 내부 단편화·COW 복사 낭비 증가
작은 페이지 → 내부 단편화·COW 복사 낭비 감소 / PTE 수와 관리 비용 증가
```

## 한 문장 봉인

> 프로세스마다 독립된 가상 주소 공간을 주고 페이지 테이블이 각 가상 페이지를 물리 프레임에 연결한다. MMU는 그 매핑과 권한을 매 접근에 적용하고 TLB는 번역 결과를 캐싱한다. 공유 가능한 물리 페이지는 함께 쓰되, COW 페이지에 실제 쓰기가 발생하면 운영체제가 그 페이지 하나만 복사하고 해당 PTE와 TLB 상태를 고친다.

## 오개념 교정 기록

- 프로그램과 프로세스를 섞어 같은 프로그램이면 같은 주소 체계를 쓴다고 생각했다. 같은 프로그램도 실행 인스턴스인 프로세스가 다르면 독립된 가상 주소 공간을 가진다.
- `프레임 7`을 주소처럼 읽었다. 프레임 7은 0부터 세는 번호이고, 4KB 프레임의 시작 주소는 28KB다.
- 프로세스 전체의 주소에 `+x`를 하는 베이스 방식과 페이지 내부 오프셋을 같은 것으로 생각했다. 페이지 오프셋은 페이지 안의 위치이고 프로세스를 구분하지 않는다.
- TLB에 실제 데이터가 캐싱된다고 생각했다. TLB에는 주소 번역과 권한이, CPU 데이터 캐시에는 실제 데이터가 저장된다.
- COW 시 페이지 테이블을 새로 만든다고 표현했다. 실제로는 물리 페이지 하나를 복사하고 쓰기 프로세스의 해당 PTE를 변경한다.
- 읽기 전용·COW·쓰기 전용이 서로 같은 수준의 하드웨어 분류라고 생각했다. COW는 운영체제가 하드웨어의 접근 권한과 예외를 이용해 만든 정책이다.
- 페이지의 4KB 안에 PTE 같은 관리 정보가 들어가 가용 공간에서 빠진다고 연결했다. PTE는 별도 페이지 테이블에 있으며, 4KB 중 사용하지 않는 공간은 관리 정보가 아니라 내부 단편화다.

## 학습 피드백

### 잘된 점

- `+x`, LinkedList, 고정 크기 조각처럼 불완전한 해법을 먼저 말하고 각 해법이 깨지는 조건을 확인하면서 페이징까지 스스로 발전시켰다.
- 가상주소 10KB와 프레임 7의 사례에서 물리주소 30KB를 직접 계산했다.
- 같은 프로그램과 서로 다른 프로세스의 개념이 섞였다는 사실을 스스로 발견해, 가상주소는 주소 공간과 함께 해석해야 한다는 구조로 교정했다.
- “캐시인데 CPU에 올려두나?”라는 질문에서 데이터 캐시와 주소 번역 캐시를 분리했다.
- COW에서 “A의 페이지를 분리하고 TLB에 반영한다”는 핵심 방향을 먼저 제안했다. 이후 보정을 통해 페이지 테이블이 정본이고 TLB는 캐시이므로, 해당 PTE를 수정한 뒤 낡은 TLB 항목을 무효화해야 한다는 관계를 연결했다.
- COW 설명 직후 “오 재밌네”라는 명시적인 재미 신호가 나왔다. 이어 `공유 → 쓰기 감지 → 한 페이지만 복사 → 매핑 변경`을 자발적으로 다시 연결한 점을 보면, 공유 구조가 쓰기 순간에 갈라지는 원인·결과의 흐름이 재미를 만든 지점으로 보인다.
- 설명의 전제나 질문의 축이 맞지 않을 때 두 번 바로 제동을 걸었다. `프레임 7`의 단위를 물은 뒤 반복 질문을 지적했고, 1KB 페이지 질문에서는 실제 사용량과 매핑 주소 범위가 섞인 전제를 반박했다. 수동적으로 답을 따르지 않고 자신의 사고 기준과 코치의 기준을 분리한 토론이었다.

### 아쉬운 점과 적용한 학습법 개선

- 학습자가 이미 30KB를 계산하고 `프레임 7`의 단위를 물었는데, 설명 직후 같은 내용을 다시 자기 말로 설명하게 했다. 새 이해를 만드는 질문이 아니라 반복 검사로 느껴졌다.
- 이를 계기로 **명확화 뒤 자동 재인출 금지**를 합의했다. 설명 부족이나 모호한 전제를 지적받으면 먼저 충분히 해결하고, 답변·계산으로 이해가 드러난 내용은 즉시 재서술시키지 않는다. 이후 실제 모순이나 빈칸이 생겼을 때만 다시 인출한다.
- `페이지 크기를 1KB로 줄이면 같은 크기의 프로세스에서 페이지 수가 4배`라는 질문은 `같은 크기`가 실제 사용량인지 동일한 매핑 주소 범위인지 불명확했다. 학습자가 내부 단편화 가능성을 지적한 뒤에야 전제를 분리했다. 이는 새 규칙 추가가 아니라 기존 **유도 질문의 전제는 명시한다** 원칙을 지키지 못한 사례다. 다음에는 `동일하게 매핑한 16KB 주소 범위`처럼 비교 기준을 질문 전에 고정한다.

학습자가 반복 검사로 느껴진 구체적 장면을 직접 지적했고, 코치가 변경 목적과 규칙을 제안한 뒤 학습자가 적용·문서화를 승인했다. 이번 회차에는 합의된 규칙 하나만 반영했다. 규칙 적용 뒤에는 MMU 같은 명확화 질문에 먼저 답하고 즉시 재서술을 요구하지 않았다. 이후 학습자는 TLB와 데이터 캐시의 구분, 프로세스별 주소 공간, COW 흐름을 자발적으로 요약했다. 한 회차의 관찰이므로 다음 학습에서도 재미와 흐름 유지 여부를 계속 확인한다.

합의한 내용은 `Level2_정리/학습법.md`와 Claude·Codex의 나선형 학습 스킬에 반영했다.
