# 51. JVM 실행 엔진(JIT·핫스팟)과 GC(도달성·mark&sweep·STW·write barrier)

**날짜**: 2026-06-29
**학습 범위**: JVM이 바이트코드를 어떻게 실행하나(인터프리터/JIT/핫스팟/추론 최적화)와, 힙의 객체를 누가 어떻게 치우나(도달 가능성/mark&sweep/GC root/STW/lost object/write barrier). **log_20 "Java GC 도달 가능성"(3줄)의 심화 재방문** — log_20이 남긴 다음 키워드 "✅ Java GC 동작 방식 심화 → GC 루트란 무엇인가, 흐름 파악"을 약 30사이클 만에 정확히 회수하고, 도달성 한 줄에서 GC 전체 메커니즘까지 끌어내렸다.

분류: JVM / 런타임 — 키워드 이해→흐름 파악 (**off-arc 탐험·학습자 주도**. 현재 hot arc 'step3 Rate Limit'와 무관 → 그 arc는 미접촉으로 유지). 재방문: log_20(도달 가능성).

## 1. 바이트코드와 JVM — "한 번 작성, 어디서나 실행"의 정체
- C 컴파일 = 그 자리에서 *특정 CPU 기계어*로 번역 → 결과물이 "그 기계 전용"이라 못 옮긴다. Java는 반대로 번역을 **2단계로 쪼갠다**(학습자가 첫 발상에서 스스로 도출).
- `javac`(= IntelliJ가 빌드 때 시킴, **미리**) → `.class` **바이트코드**. 바이트코드는 **현실의 어떤 CPU 것도 아닌, 가상 기계(JVM)를 위한 명령어**. 그래서 "Virtual Machine" — 명세로만 정의된 가짜 CPU, 바이트코드는 그 가짜 CPU의 기계어.
- 바이트코드 → 진짜 기계어, 이 **뒤쪽 절반**은 **JVM이 런타임에** 한다. JVM은 **명세(spec) vs 구현(implementation)**이 분리 — x86 윈도우용·ARM 맥용·x86 리눅스용 구현체를 각각 따로 만들어 같은 바이트코드를 자기 플랫폼 기계어로 번역.
- 학습자의 첫 "오버라이드" 비유 교정: 플랫폼마다 갈아끼는 단위는 **메서드 하나하나가 아니라 JVM 구현체 통째**. 방향(다형성)은 맞았고 단위만 한 칸 위로.
- 오개념 교정: "IntelliJ가 미리 컴파일"은 **앞쪽 절반(소스→바이트코드)만**. JIT는 경쟁자가 아니라 **이어달리기 뒤 주자**. `[.java]→javac(미리)→[.class]→JIT(실행 중)→[기계어]`.

## 2. 인터프리터 vs JIT — 핫스팟만 골라 컴파일
- **인터프리터**(한 줄씩 해석): **시작 빠름**. 단 같은 코드 백만 번이면 백만 번 재해석 → 누적 손해.
- **AOT식 전체 선번역**: 실행 효율↑, 단 저장 공간·초기 지연. 거의 안 쓸 코드(초기화·예외분기)까지 비싸게 번역.
- 둘 다 "자기가 제일 못하는 곳에 힘을 쏟는" 모순 → **학습자가 직접 조합 도출**: "몇 번 이상 반복되는 메서드만 번역, 한 번 쓰는 건 인터프리터." 이게 곧 **JIT(Just-In-Time)**.
- JVM은 메서드마다 **호출/루프 카운터**를 세다가 **임계값(threshold)** 넘으면 "hot"으로 판정해 백그라운드 컴파일 → 다음 호출부터 기계어 버전으로 교체. 자주 타는 지점 = **핫스팟**, 그래서 오라클 구현체 이름이 **HotSpot JVM**. 한 프로그램 안에서 인터프리터와 컴파일 코드가 **공존**.

## 3. 추론 최적화(speculative) — 관찰 데이터로 거는 도박 + guard/deopt
- JIT는 번역 시점이 **이미 한참 돈 뒤**라, **C 컴파일러는 영원히 못 가지는 "실제 실행 이력"**을 손에 쥔다.
- 예: `a.sound()` 다형성 호출이 만 번 내내 `Dog`였다면 → **"Dog일 것"이라는 가정을 박고** 매번 타입 확인을 들어냄. 본문이 짧으면 호출 자체를 펼쳐 넣음(**인라이닝**). = **speculative optimization**(학습자가 "Dog 미리 로드" + "틀리면 다 날리는 비용"을 스스로 지목).
- 안전장치: 입구에 싼 체크 = **guard**("진짜 Dog 맞나"). 깨지면 최적화 버전 폐기하고 인터프리터로 되돌림 = **deoptimization**. 핵심은 *기댓값 플러스 도박* — 만 번 Dog였으면 만천 번째도 Dog일 확률이 압도적이라, 가끔 지는 비용보다 평소 이득이 큼.

## 4. stack vs heap — 수명으로 공간을 가른다
- `int x`처럼 **크기 명확·메서드와 운명 동일** → **스택**(들어온 순서대로 쌓였다가 메서드 끝나면 프레임 통째 걷어냄. 정리 규칙이 못박혀 있어 고민 없음).
- `new`로 만든 객체처럼 **수명이 메서드를 넘어설 수 있음**(return·전역 리스트 등록) → **힙**. 메서드 끝나는 시점만으론 "버려도 되는지" 판단 불가.
- 학습자가 분리 기준을 **"수명"**으로 정확히 잡음 → 공간을 나누는 *이유* 자체가 그것.

## 5. GC — 도달 가능성과 mark & sweep
- "버려도 된다" = **아무도 안 가리킨다 = 루트에서 도달 못 한다** = **도달 가능성(reachability)**. 메서드 종료 시점이 아니라 *참조가 살아있느냐*로 판단(log_20에서 3줄로 본 그 개념을 메커니즘으로 확장).
- **연쇄(chain)**: `b→Box→Point`. 한 칸 끊기면 그 아래 줄줄이 회수 가능. 참조는 스택만이 아니라 **다른 힙 객체의 필드 안**에도 산다(Box.content) → 스택만 봐선 안 됨.
- **방법 A vs B**(학습자가 B 선택):
  - A: 모든 객체에 "너 가리키는 사람 있어?" 역으로 물음 → 모든 참조를 다 훑어야 해서 비쌈.
  - **B(mark&sweep)**: **루트에서 정방향으로 따라가며 "살았음" 도장(Mark)** → 안 닿은 나머지를 쓸어버림(**Sweep**). Garbage는 **한 번도 안 쳐다봄**, "안 닿은 나머지"로 자동 분류.
- **왜 dead가 아니라 alive를 마킹하나**(학습자 질문): 자바엔 `free()`가 없어 **객체가 죽는 "순간"이 선언되지 않는다**. 죽는 순간 마킹하려면 객체마다 참조 수를 세는 **Reference Counting**이 필요한데 → (1) 모든 대입이 카운터 갱신이라 비쌈 (2) **순환(A↔B)**은 카운트 0이 안 돼 누수. mark&sweep은 "언제 죽었나"를 포기하고 "지금 도달 가능한가"만 물어 둘 다 회피.
- **GC root** = 따라가기 시작점 = 스택 지역변수 + static 필드 등.
- **트리거는 시간(타이머)이 아니라 메모리 압력** — 힙(Eden)이 차면 터짐. 그래서 GC 타이밍은 불규칙(할당 속도에 좌우). 죽은 객체가 *즉시* 안 치워지고 다음 GC까지 남는 = **floating garbage**(학습자가 일찍 "수거까지 시간이 걸린다"로 직관).
- 도장은 영구 표식이 아니라 **매 사이클 리셋** 후 루트부터 다시 찍음.

## 6. STW와 lost-object — 동시성이 마킹을 깨는 법
- GC가 마킹하는 *그 찰나* 앱이 그래프를 바꾸면 판단이 깨질 수 있다. **lost-object 시나리오**(학습자가 A/C/B로 정확히 재구성):
  - 시작: `Root→PENDING→VICTIM`(VICTIM 살아있음). GC가 `DONE`을 "다 봤음"으로 마킹.
  - 앱이 ① `DONE.x = VICTIM`(이미 다 본 객체에 새 참조) ② `PENDING.f = null`(원래 경로 끊김).
  - VICTIM의 유일한 길은 DONE뿐인데 DONE은 다시 안 봄 → **살아있는 VICTIM을 오수거** 💥.
- 해결책 = **Stop-The-World(STW)**: GC가 일하려 **앱(=세상)을 통째로 얼린다**(멈추는 건 GC가 아님 — 학습자의 "GC가 블락" 방향 교정). 앱이 안 움직이면 ①② 두 줄이 실행 불가 → 오수거 원천 봉쇄. **이게 STW가 안전한 이유.**
- "GC를 멈추면 되잖아"(학습자) 교정: **급함이 아니라 일관성 문제**. 창고 재고조사 비유 — 조사자를 멈췄다 재개해도 그새 인부들이 박스를 옮겨 절반이 무효. GC를 멈추는 건 문제를 *미룰* 뿐. 그래서 **인부(앱)를 세운다**.
- 트레이드오프: STW는 안전하나 힙 클수록(수 GB) 멈춤 길어짐 → "자바 서버가 0.5초 뚝 끊김"의 정체 = **GC pause**. JVM GC 역사 = "이 멈춤을 어떻게 줄이나"의 싸움.

## 7. write barrier — 앱 안 멈추고 마킹 지키기
- 사고 원인은 **항상 "참조 필드에 값을 쓰는" 한 종류의 연산**(`a.field = b`). 그러면 앱 전체를 멈추는 대신 **그 쓰기에만 검문소**를 단다 = **write barrier**(모든 *write*가 통과하는 *barrier*).
- 학습자가 검문소의 동작을 **스스로 두 변종 설계**(둘 다 정답):
  1. **VICTIM을 to-do(회색)에 넣어 마킹** / 2. **DONE을 "처리 안 됨"으로 되돌려 재검사** → 둘 다 "새 참조 생김(write ①)"에 반응 = **Incremental Update**(Dijkstra). (정밀화: VICTIM을 "끝(검정)"이 아니라 "to-do(회색)"로 — 그래야 VICTIM의 자식도 따라감. 검정/회색/흰색 = **삼색 마킹**, 학습자가 사실상 굴림.)
  - 안 가본 길: **SATB(Snapshot-At-The-Beginning, Yuasa)** — write ②(옛 참조 끊김)에 검문소를 달아 *밀려나는 옛 값(VICTIM)을 죽기 직전 낚아채* "시작 시점 스냅샷"을 보존. **자바 G1 GC가 이 방식.**
- 트레이드오프(STW vs barrier): STW = *가끔 한 번에 길게* 멈춤 / barrier = 모든 참조 쓰기에 코드가 끼어 *평소에 조금씩 꾸준히* 무거움(상수 세금). **응답성을 위해 처리량을 약간 내주는 거래.**

## 한 문장 봉인
> JVM은 바이트코드를 **인터프리터로 빨리 시작**하다 **핫스팟만 JIT 컴파일**하고(실행 이력을 근거로 **추론 최적화**+guard/deopt), 힙의 객체는 **루트에서의 도달 가능성**으로 살리고(**mark&sweep**, dead가 아니라 alive를 찍는 건 죽는 순간이 선언되지 않고 순환 누수를 피하기 위함), 마킹 중 그래프 변경이 산 객체를 죽이는 **lost-object**를 **STW(세상을 멈춤)**나 **write barrier(쓰기마다 검문)**로 막는다 — 둘은 "한 번에 길게 vs 조금씩 꾸준히"의 트레이드오프.

### 잘된 것
- **"추측 먼저"가 거의 모든 길목에서 작동.** JIT 조합("핫코드만 번역"), speculative load와 폐기 비용, mark&sweep 방법 B, write barrier 두 변종 — 핵심 개념을 *코치가 주기 전에 학습자가 도출*했다. 특히 **lost-object 시나리오를 자기 언어(A/C/B)로 정확히 재구성**한 건 체득 신호.
- **오개념을 즉시·정직하게 교정.** "오버라이드 단위(메서드→구현체)", "IntelliJ가 미리 컴파일(앞쪽 절반만)", "GC를 멈추면 됨(일관성 비유)", "GC가 블락(앱이 블락)", 그리고 ①번 떨어뜨림 시나리오는 *사실 GC가 옳았다*고 정정하며 진짜 위험은 반대 방향임을 드러냄 — 미루지 않고 그 자리에서 닫음.

   - 행동: (a) 다개념 응답은 **첫 개념 하나에서 끊고** "여기까지 잡히면 다음 갈까요?" (b) **재방문 인출 퀴즈는 힌트 없이 선택지만**, 명시적으로 막힌 뒤에만 힌트. (한 사이클 하나 — '과잉공급 절제' 한 테마.)

*off-arc 탐험이었다 — 형식상 다음 칸은 여전히 **hot arc 'step3 Rate Limit'의 #3(거부정책)·#4(재시도안전)·#5(서킷브레이커)**다(미접촉 유지). JVM을 계속 탈지, Rate Limit arc로 복귀할지는 학습자 선택.*

**JVM에서 새로 열린 씨앗(본문/cold 보관):**
- **세대 구분 GC(Minor/Major, Young/Old)** — log_20이 예고했으나 오늘 미답(STW 트레이드오프에서 이름만 스침). "왜 힙을 세대로 나누나 = 대부분 객체는 일찍 죽는다(weak generational hypothesis)".
- **계층형 컴파일(C1/C2)** — JIT 안에 컴파일러가 여러 단계인 이유(왜 한 번에 최고 수준으로 안 하나).
- **write barrier 구현 깊이** — SATB vs incremental update 선택 기준, G1/ZGC가 실제로 쓰는 방식.
