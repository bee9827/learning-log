# 72. 동기·비동기와 블로킹·논블로킹 — 호출, 반환, 작업 완료의 순서

**날짜**: 2026-09-28~29

**학습 범위**: 두 분류 축을 시간 순서로 구별하고 `tryConsume()`, `Future`, `Object.wait()`에 적용

**재방문**: [#20 동기 리스너 호출](20_옵저버-EventListener.md), [#52 블로킹 토큰 대기](52_거부정책-대기시간x동시대기자수-boundedWait-checkThenAct.md), [#67 스레드 실행 상태](67_스레드-실행상태-플랫폼-가상스레드.md)

## 출발점 — 두 축이 모두 기다림처럼 들렸다

처음에는 “비동기 = 다른 스레드에 맡긴다”, “논블로킹 = 기다리지 않고 어떻게든 일을 해낸다”, “논블로킹이려면 비동기가 필요하다”로 추측했다. 동기·비동기와 블로킹·논블로킹을 각각 문장으로 들으면 납득됐지만, 스스로 떠올리기는 어려웠다. 두 설명 모두 ‘기다림’을 말하는 것처럼 들렸기 때문이다.

## 기억의 기준점: 호출 → 반환 → 작업 완료

```text
호출 ───── 반환 ───── 작업 완료
```

- **동기/비동기**: 관심 있는 작업의 완료를 **시작 호출 안에서 확인해야 하는지**를 본다. 동기는 이번 호출의 결과를 확정하고 반환한다. 비동기는 시작 호출이 작업 완료를 기다릴 의무가 없고, 완료를 `Future`·콜백·이벤트 같은 별도 경로에서 다룬다. 보통은 반환 뒤에 완료되지만, 이미 완료된 `Future`를 즉시 반환할 수도 있다.
- **블로킹/논블로킹**: 기다려야 할 때 **호출한 쪽이 대기 때문에 멈추는지**를 본다. 멈춰 기다리면 블로킹, 기다리지 않고 돌아와 다른 일을 할 수 있으면 논블로킹이다.
- 기준 작업을 명확히 해야 한다. 비동기 메서드가 즉시 `Future`를 반환해도, 그 `Future`는 **실제 작업의 최종 결과가 아니라 결과를 나중에 받을 수단**이다.

| 장면 | 결과가 오는 흐름 | 호출한 쪽의 대기 |
|---|---|---|
| 토큰 없는 `tryConsume()` | 즉시 `false`로 **이번 시도**를 완료하고 반환 → 동기 | 토큰이 찰 때까지 기다리지 않음 → 논블로킹 |
| Java `Object.wait()` | 기다림이 끝난 뒤 `wait()` 호출에서 반환 → 동기 | 호출 스레드가 기다림 → 블로킹 |
| 비동기 작업을 시작하고 `Future`를 받음 | 시작 호출과 완료 처리를 분리 → 비동기. 보통 나중에 완료되지만 이미 완료됐을 수도 있음 | 시작 호출은 완료를 기다릴 의무가 없음 |
| 그 뒤 `Future.get()` 호출 | 원래 작업은 비동기로 시작했지만 결과를 회수하는 이 호출은 기다린 뒤 반환 | `get()`에서 블로킹 |

`tryConsume()`이 `false`로 끝날 수 있다는 반례가 중요했다. **논블로킹은 반드시 성공시킨다는 뜻이 아니다.** 이번 시도에서 할 수 없다는 결과를 바로 줘도 논블로킹이다. “지금 없어도 언젠가 반드시 성공해야 한다”는 요구가 추가되면 나중에 다시 호출하거나 완료 통지를 받는 설계를 따로 선택한다.

## 별도 스레드가 없어도 비동기일 수 있다

하나의 애플리케이션 스레드가 네트워크 요청을 시작하고, 응답을 기다리는 동안 다른 코드를 실행한 다음, 응답 도착 후 같은 스레드에서 완료 처리를 할 수 있다. 비동기는 **시작 호출과 완료 처리를 분리하는 관계**이며, 다른 스레드는 그 관계를 구현하는 한 방법일 뿐이다. 네트워크·운영체제가 응답을 진행시키는 동안 애플리케이션 스레드는 다른 일을 한다. 단일 스레드가 CPU 계산 두 개를 동시에 실행한다는 뜻은 아니다. 긴 계산이 그 스레드를 차지하면 완료 처리도 밀린다.

`Future`를 반환받은 변수 자체가 나중에 다른 값으로 바뀌는 것은 아니다. 같은 `Future`의 상태가 미완료에서 완료로 바뀌고 결과를 확인할 수 있게 된다. `get()`으로 그 결과를 기다리면 그 지점은 블로킹이다.

Java의 `Object.wait()`는 위 기준에서 동기·블로킹이다. 다만 `wait()`가 끝났다는 것과 애초에 기다리던 **조건이 참이 됐다**는 것은 다르다. 깨어난 뒤 조건을 재확인해야 한다.

## 학습자가 직접 봉인한 기준

> 호출 반환 작업완료  
> 반환 먼저하고 결과 나중에오면 비동기  
> 결과 나오고 반환하면 동기  
> 호출하는 쪽이 기다리면 블로킹  
> 기다리지 않으면 논블로킹

이때 “결과”는 `Future` 같은 접수증이 아니라 **관심 있는 실제 작업의 최종 결과**로 읽는다. 이 시간선은 흔한 비동기 실행을 기억하기 위한 그림이지 모든 호출의 필수 순서는 아니다. 비동기 API가 이미 완료된 결과를 반환할 수도 있고, 최종 반환값 없이 완료 이벤트만 보낼 수도 있다. 무엇을 “작업”으로 볼지도 먼저 정해야 한다. 예를 들어 큐에 넣기는 동기로 끝나도 큐에 들어간 실제 처리는 비동기일 수 있다.

## 학습 방식 회고

- 추상적인 두 질문을 외우는 방식은 듣고 나면 맞았지만 스스로 인출되지는 않았다. **호출 → 반환 → 작업 완료**라는 시간 축을 그리자 학습자가 바로 자기 말로 두 축을 재구성했다. 다음에도 용어 쌍을 표로 시작하기보다 사건 순서를 먼저 잡는다.
- #71의 “질문 대상을 정확히 읽기”는 `wait()` 질문에서 Java `Object.wait()`라는 전제를 명시하는 방식으로 적용했다. 별도 문법·코드 요청은 없었다.
- 아쉬운 점: 초반의 정의 중심 설명과 반복 분류 질문만으로는 기억의 손잡이가 생기지 않았다. 다음에는 학습자가 재인출에 막히는 순간 더 짧은 **흐름 그림**으로 바꾼다.
