# 60. URL 한 줄부터 화면까지 — 포트·TCP 순서번호·TLS 신뢰 사슬·Tomcat 두 책임

**학습 범위**: `https://앱/reservations` 엔터부터 암호화된 응답이 화면에 뜨기까지의 전 계층. 네트워크(DNS·포트·TCP)와 Tomcat 내부(서블릿 컨테이너·WS/WAS)와 TLS(신뢰 사슬)를 하나의 여정으로 꿰었다. Spring 웹 흐름(log_15·21)보다 **한 층 아래**.

## 다리 A — URL에서 서버 문 앞까지

- **DNS**: 도메인 이름은 사람이 외우기 쉬우라고 붙인 **별명**. 실제 네트워크 장비(라우터)는 숫자 **IP로만 길을 찾는다** → DNS가 별명 → 숫자 번역.
- **포트 = 건물(IP)의 문 번호**. 한 컴퓨터 안 여러 프로그램이 각자 다른 문을 쓴다. 서버 프로그램은 특정 문을 열고 **listen**(요청 대기).
  - 80(HTTP)·443(HTTPS)은 **약속된 기본 문** → 브라우저가 자동으로 채워 생략 가능.
  - `8080`은 기본이 아니라 **Spring의 Tomcat이 연 문** → 직접 명시해야 함. (dev에서 80 대신 8080 쓰는 건 낮은 번호 문은 관리자 권한이 필요해서.)

## Tomcat은 두 가지 책임을 진다

1. **연결·번역 책임**: 포트에서 TCP 연결을 받고 → 바이트를 HTTP로 **파싱** → **HttpServletRequest**(구조화된 객체) + 빈 HttpServletResponse 생성 → 처리할 **스레드 배정**.
   - 여기 **Tomcat 스레드 풀**이 곧 "동시 요청 스레드"의 출처 — 내가 씨름한 CAS·락 경합(log_47·55·56)의 스레드들이 여기서 나온다.
2. **서블릿 컨테이너 책임**: 그 request를 **서블릿(DispatcherServlet)**에게 넘겨 실행·관리(생명주기·호출).

- **Servlet vs Tomcat**: Servlet은 "HTTP 요청 하나를 처리하는 **표준 계약**(`service(req,res)`)" = 규격. Tomcat은 그 규격의 부품들을 담아 돌리는 **서블릿 컨테이너**. DispatcherServlet은 그 규격을 따르는 하나의 부품.
- **WS vs WAS**: 정적 파일만 주는 WS(nginx)는 **1번 책임만**. 코드를 실행하는 WAS(Tomcat)는 **2번 책임까지**. 그 선이 둘을 가른다. (실무: nginx(WS) 앞단 + Tomcat(WAS) 뒤 — 각자 잘하는 책임.)

## TCP 3-way handshake — 왜 하나

- HTTP 바이트를 흘리기 전에 TCP가 먼저 "연결하자" 악수. 이유 = **순서대로·빠짐없이 전달**이라는 약속을 지키려고.
- 데이터는 여러 **조각(패킷)**으로 쪼개져 따로 날아가 순서가 뒤바뀌거나 유실될 수 있다 → 각 조각에 **순서 번호(sequence number)** = 책 페이지 번호. 받는 쪽이 빠진 조각·순서를 안다.
- handshake = 양쪽이 **시작 순서 번호(ISN)**를 서로 맞추는 자리.
- **ISN은 매 연결 랜덤한 큰 값**. 왜 1 고정이 아닌가:
  1. **주입 방어**: 예측 가능하면 눈먼(트래픽 못 보는) 공격자가 가짜 조각의 순서 번호를 맞혀 끼워넣기 쉬움. 랜덤이면 맞혀야 해서 어려움. (트래픽을 *볼 수 있는* 공격자는 못 막음 → 기밀은 TLS 담당.)
  2. **유령 패킷 방지**(원래 이유): 같은 포트 쌍으로 새 연결을 열었을 때, 이전 연결의 늦게 온 조각이 새 연결 데이터로 오인되는 것을 방지.

## TLS — 도청당하는 길에서 비밀 통신하기

- **위치**: `https`면 요청·응답 바이트가 암호화. 오늘 [인증 카드](../Level2_정리/인증세션.md)의 **기밀성 vs 무결성**과 직결 — JWT Signature는 무결성만, **기밀성은 TLS가 준다**. TLS = 기밀성 + 무결성 + 서버 인증.
- **퍼즐**: 암호화하려면 양쪽이 같은 비밀 열쇠를 알아야 하는데, 처음 만난 사이 + 공개된 길. 열쇠를 그냥 보내면 엿보는 자도 안다.
- **해결(비대칭키)**: 서버가 **열린 자물쇠(공개키)**를 뿌림 → 누구나 잠글 수 있지만 **여는 열쇠(비밀키)는 서버만**. 공개키·비밀키 **둘 다 서버 것**, 클라이언트는 자기 키 쌍 없이 서버 공개키를 받아 씀.
- **세션 키**: 공개키 암호는 **느려서** 실제 데이터엔 안 씀. 공개키로는 **이번 연결용 대칭 세션 키** 하나만 안전하게 정하고(클라가 세션 키를 상자에 넣어 서버 공개키로 잠가 보냄 → 서버만 엶 → 둘 다 같은 세션 키 보유), 실제 요청·응답은 **빠른 세션 키**로. 양쪽이 잠깐 들고 연결 끝나면 버림.
- **MITM(중간자)**: 탈취자가 서버 공개키 대신 **자기 공개키를 끼워넣으면** 다 읽는다.
- **방어 = 인증서 + CA**: 공개키는 벌거벗고 안 오고 **인증서 봉투**에 담겨 옴 — "이 공개키는 naver.com 것" + **CA의 서명**. 탈취자가 봉투 안 공개키를 바꾸면 **서명이 깨져** 들통(← 오늘 JWT Signature 원리: 재계산·비교, secret 없으면 위조 불가). 탈취자는 CA 비밀키가 없어 다시 서명 못 함.
- **신뢰의 뿌리**: CA 서명을 검증할 **CA 공개키는 네트워크로 받으면 또 뚫림** → **OS/브라우저에 미리 내장**(root 인증서 목록 = trust anchor). 여기 못 박혀서 안 뚫림.
- **사슬**: 내장 CA 공개키 → naver 인증서의 CA 서명 검증 → naver 공개키 신뢰 → 세션 키 안전 교환 → 암호화 통신.
- **양방향**: 응답도 나갈 때 **세션 키로 암호화** → 브라우저가 세션 키로 복호화해 렌더링. "화면에 뜬 목록"은 중간 내내 암호문이었다.

## 여정이 맞물리는 지점 (오늘의 수확)

> Tomcat이 HttpServletRequest를 만들어 **DispatcherServlet에 넘긴다** — 이게 [Spring 웹 흐름 카드](../Level2_정리/Spring웹흐름.md)의 **첫 줄**. 오늘은 그 **이전(네트워크)**과 **속(Tomcat 두 책임·TLS)**을 파냈다. 네트워크 층 ↔ 애플리케이션 파이프라인이 여기서 맞물린다.

## 학습법 회고

- **잘된 것**: 추측 먼저 → 후보 탈락 루프가 끝까지 돌았다. 특히 학습자가 **MITM 공격을 스스로 발명**("Client Key를 우리 걸로 바꿔 보내면 볼 수 있잖아")하고, ISN 랜덤화의 이유·CA 서명의 필요성을 추론으로 도출. 오늘 낮 JWT Signature 학습이 CA 서명 이해에 그대로 재사용됨(재방문 엔진 작동).
- **바꿀 것 적용**: 종합_2부의 "원리로 닫히는 매듭은 미탐구로 미루지 않는다"를 적용 — TLS를 씨앗으로 미루지 않고 그 자리에서 신뢰 사슬 끝까지 닫음.

## 퀴즈에서 걷어낸 오개념 (재방문 시 주의)

- **"클라이언트 키" 같은 건 없다** (3회 미끄러진 지점). 공개키·비밀키 **둘 다 서버 것**. 클라이언트는 서버 공개키를 받아 쓸 뿐.
- **CA는 암호화(기밀성)하지 않는다 — 서명(무결성)한다.** 인증서는 암호화 안 됨(공개, 누구나 읽음). ← 오늘 인증 카드 기밀성 vs 무결성. 탈취자를 막는 건 두 겹: ① 세션키 상자는 **서버 비밀키가 없어** 못 엶(암호화) + ② 공개키 바꿔치기는 **CA 서명이 깨져** 들킴(서명).
- **공개키는 사용자마다가 아니라 사이트(서버)마다 하나** (naver의 신분증). 연결마다 다른 건 세션키.
- **세션키는 밖에서 주입받는 게 아니라 브라우저가 자기가 생성**한다 → 탈취자가 자기 세션키를 피해자에게 "밀어넣기" 불가. 강제하려면 MITM 필요 → 인증서 벽에 막힘.
- **위협 모델 = 선(wire) vs 기기(endpoint)**: TLS는 선을 지킨다. 기기 안에 코드를 심을 수 있으면 세션키도 필요 없이 평문 화면을 읽으면 되므로 — 그건 TLS 소관 밖(자기모순). "저장소에 밀어넣기"가 되는 순간 이미 TLS가 지키는 범위 밖.

## 씨앗 (본문에만)

- **디피-헬만(DH) 키 교환**: 세션 키를 아예 보내지 않고 양쪽이 각자 계산해 같은 값에 도달(forward secrecy). 현대 TLS의 실제 방식.
- **DNS 내부 동작**: recursive resolver·캐싱·계층(root→TLD→authoritative).
- **HTTP 버전**: HTTP/1.1 vs 2 vs 3(QUIC) — 연결·멀티플렉싱 차이.
