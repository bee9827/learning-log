# 75. CPU 캐시 — 캐시 라인·지역성·계층과 TLB의 역할 구분

**날짜**: 2026-10-03  
**분류**: 일반 CS (컴퓨터 구조) — 프로젝트 외, 미러 제외  
**재방문**: [#66 CPU 명령어 사이클](66_CPU-명령어사이클-레지스터-인터럽트.md), [#64 가상주소·페이지·TLB](64_가상주소-페이지-프레임-MMU-TLB.md), [#67 스레드 실행 상태](67_스레드-실행상태-플랫폼-가상스레드.md)

## 출발점 — RAM에서 매번 가져오면 어떤 비용이 드나

#66의 단순화한 인출 흐름은 `PC → MAR → RAM → MBR → IR`이었다. 처음에는 “자주 쓰는 IR을 저장하면 되지 않을까?”라고 추측했다. IR은 현재 명령어를 담는 레지스터이고, CPU 캐시는 메모리에서 읽은 **명령어와 데이터의 복사본**을 보관한다. 레지스터가 값을 이미 갖고 있다면 연산 중 재사용할 수도 있지만, 캐시와 레지스터는 역할이 다르다.

## 한 값을 읽는 시간선

~~~text
프로그램이 numbers[0]의 가상주소로 접근
→ TLB의 번역 결과를 쓰거나, 없으면 페이지 테이블을 확인
→ 번역·접근 권한 확인
→ L1 데이터 캐시에서 값을 찾고, 없으면 아래 캐시·RAM을 확인
→ 캐시 미스 시 주변 바이트를 포함한 캐시 라인을 가져옴
→ 필요한 값을 레지스터에 넣어 연산
~~~

실제 CPU에서는 주소 번역과 L1 캐시 후보 조회의 일부가 겹칠 수 있다. 위 시간선은 **논리적 의존 관계**다. [Arm의 VIPT 캐시 설명](https://developer.arm.com/community/arm-community-blogs/b/architectures-and-processors-blog/posts/page-colouring-on-armv6-and-a-bit-on-armv7)

## 왜 한 값보다 주변 값을 같이 가져오나

작은 `int[] numbers`를 순서대로 읽을 때 `numbers[0]`의 첫 접근은 캐시 미스라고 가정했다. 이때 가져온 캐시 라인에 `numbers[1]`도 포함돼 있다면 다음 접근은 히트한다. 가까운 주소를 곧 쓸 가능성이 **공간 지역성**이다. 같은 작은 배열을 두 번째로 순회할 때 라인이 여전히 남아 있다면 다시 히트한다. 가까운 시간 안에 같은 데이터를 재사용하는 것이 **시간 지역성**이다.

주변 바이트를 가져오는 일이 항상 이득은 아니다. 먼 주소만 무작위로 읽으면 사용하지 않을 데이터의 전송·캐시 공간 비용이 생긴다. 스레드 A가 배열을 캐시에 올린 뒤 같은 코어에서 스레드 B가 큰 배열을 훑으면, B의 접근이 A의 라인을 밀어낼 수 있다. 컨텍스트 스위치 자체가 A의 캐시를 지우는 것은 아니다. 캐시는 스레드별 저장 공간이 아니라 코어가 사용하는 하드웨어 자원이다.

## L1·L2·L3와 쓰기

작고 빠른 L1에서 시작해, 미스가 나면 더 큰 L2·L3와 RAM으로 내려간다. L1은 보통 코어별이고 L3는 여러 코어가 공유하는 설계가 흔하다. L1 미스라도 L2에 있을 수 있고, B가 많은 데이터를 만졌다면 L3에서도 밀려났을 수 있다. 여러 단계는 접근 지연·용량·칩 면적의 절충이다. [Arm 캐시 계층](https://learn.arm.com/learning-paths/servers-and-cloud-computing/memory-subsystem/cache-hierarchy/), [Intel 캐시 계층](https://www.intel.com/content/dam/www/public/us/en/documents/white-papers/cache-allocation-technology-white-paper.pdf)

일반적인 write-back 캐시에서는 수정한 캐시 라인을 RAM에 즉시 기록하지 않을 수 있다. 다른 코어가 같은 라인의 복사본을 갖고 있다면 캐시 일관성 장치가 무효화·전달 등을 조정한다. 다른 코어가 새 값을 얻는 데 RAM 기록이 선행해야 하는 것은 아니다. 레지스터·컴파일러 최적화와 Java 가시성 보장은 별도 노드 [#76](76_가시성-코어캐시-레지스터-volatile.md)로 분리했다. [Intel 코어 간 데이터 전달](https://www.intel.com/content/www/us/en/developer/articles/technical/fast-core-to-core-communications.html)

## 세 종류의 ‘없음’

| 사건 | 빠른 곳에 없는 것 | 다음 확인 |
|---|---|---|
| TLB 미스 | 가상 페이지 → 물리 프레임 번역 | 페이지 테이블 |
| 데이터 캐시 미스 | 실제 명령어·데이터 | 아래 캐시 또는 RAM |
| 페이지 폴트 | 유효한 매핑·접근 권한 또는 현재 상주 페이지 | OS 처리 |

페이지 테이블은 가상 페이지와 물리 프레임의 **원본 연결 정보**, TLB는 그 **번역 결과의 캐시**, CPU 데이터 캐시는 **내용물의 캐시**다. TLB 미스여도 페이지 테이블에 유효한 연결이 있으면 페이지 폴트 없이 계속할 수 있다. TLB 기록만 밀려나고 실제 데이터는 CPU 캐시에 남을 수도 있다. 다만 페이지 테이블을 읽는 작업에서 캐시 미스가 나면 RAM 접근이 생길 수 있다. [Linux 커널의 TLB 설명](https://docs.kernel.org/next/core-api/cachetlb.html)

## 한 문장 봉인

> CPU 캐시는 실제 명령어·데이터를 캐시 라인 단위로 가까이 두고 공간·시간 지역성을 이용한다. 주소 번역은 페이지 테이블과 TLB의 몫이며, 번역 미스·데이터 캐시 미스·페이지 폴트는 각각 다른 사건이다.

## 학습 방식 회고와 다음 씨앗

- 배열의 첫 접근→인접 원소→두 번째 순회→다른 스레드의 큰 배열이라는 시간선으로 지역성과 축출을 연결했을 때 흐름이 잡혔다.
- ‘메모리’라는 말로 RAM·CPU 캐시·레지스터·커널 메모리를 뭉뚱그려 설명하면 가시성의 원인을 오해했다. 이후에는 물리적 위치와 Java의 보장을 분리해 말한다.
- 다음 씨앗: 캐시가 꽉 찼을 때 어떤 라인을 남기는지(교체·충돌 미스), TLB·캐시 조회가 겹치는 실제 하드웨어 경로. 현재 hot은 가상 스레드 스케줄러이므로 BACKLOG에 새 줄은 추가하지 않는다.
