## 왜 스레드마다 실행 상태가 필요한가

스레드는 프로세스의 자원을 이용해 독립적으로 명령어를 따라가는 실행 흐름이다. 두 스레드가 PC와 호출 스택 하나를 공유하면, 한 스레드가 `pop`한 뒤 다른 스레드의 복귀 주소로 이동할 수 있다.

```text
프로세스가 공유하는 것 → 코드, 힙, 열린 파일 같은 주소 공간과 자원
스레드마다 다른 것    → PC·레지스터 상태, 스택, 현재 실행 위치
```

같은 프로세스의 스레드는 같은 가상 주소 공간을 사용한다. 각 스레드의 스택은 그 주소 공간 안에서 서로 다른 영역을 할당받고, SP(Stack Pointer)가 자기 스택의 현재 위치를 가리킨다.

## 문맥 교환은 스택 전체를 복사하지 않는다

CPU가 스레드 A에서 B로 바꿀 때 A의 스택 전체를 치웠다가 복사하지 않는다. 스택 내용은 원래 메모리 영역에 남겨두고 PC·SP·일반 레지스터와 상태값을 저장한다.

```text
A에서 내려갈 때 → A의 PC·SP·레지스터 상태 저장
B를 올릴 때     → B의 PC·SP·레지스터 상태 복원
SP가 바뀜       → CPU가 바라보는 호출 스택도 B의 영역으로 바뀜
```

사용자 모드에서 애플리케이션을 실행할 때 쓰는 사용자 스택과, 시스템 콜·인터럽트 등으로 커널 코드를 실행할 때 쓰는 커널 스택도 구분된다. 세부 배치는 OS와 CPU 구조에 따라 달라지지만, 핵심은 중단된 실행 흐름이 돌아올 수 있도록 최소 상태를 보존한다는 것이다.

## 플랫폼 스레드와 스레드 풀

Java 플랫폼 스레드는 보통 OS 스레드와 1:1로 대응한다. 플랫폼 스레드가 완전히 종료되면 대응하는 OS 스레드도 종료되지만, 백엔드 서버는 생성·제거 비용을 줄이려고 플랫폼 스레드를 풀에 넣어 작업마다 재사용한다.

```text
Tomcat 스레드 풀에서 플랫폼 스레드 대여
→ Controller → Service → DAO를 같은 스레드가 실행
→ ThreadLocal의 트랜잭션 커넥션 사용
→ 트랜잭션과 ThreadLocal 정리
→ 플랫폼 스레드를 풀에 반납
```

요청이 끝나도 스레드는 살아서 다음 요청에 재사용된다. 그래서 ThreadLocal을 정리하지 않으면 이전 요청의 값이 다음 요청으로 누출될 수 있다. #09에서 배운 “같은 스레드라서 같은 커넥션이 전파된다”는 장점과 “재사용 전에 반드시 정리해야 한다”는 위험이 같은 구조에서 나온다.

OS 스레드 수와 CPU 논리 프로세서 수도 다르다. OS는 논리 프로세서보다 훨씬 많은 스레드를 만들고, 실행 가능한 일부만 CPU에 번갈아 올린다. CPU 중심 작업은 스레드가 코어 수보다 지나치게 많으면 문맥 교환 비용이 커지지만, I/O 중심 작업은 일부 스레드가 기다리는 동안 다른 스레드가 실행할 수 있어 코어 수보다 큰 풀이 의미가 있다.

## 가상 스레드가 필요한 이유

플랫폼 스레드가 I/O를 기다리면 CPU 코어를 계속 점유하지는 않지만, OS 스레드와 그 스택·관리 자원은 작업에 묶여 있다. 동시 I/O 요청이 매우 많으면 스레드 풀이 먼저 고갈될 수 있다.

가상 스레드는 JVM이 관리하는 가벼운 실행 흐름이다. 실제 CPU에서 실행할 때는 플랫폼 스레드인 **캐리어(carrier)**에 잠시 올라간다.

```text
가상 스레드 A가 캐리어 P1에 mount
→ Java 코드 실행
→ 지원되는 blocking I/O에서 대기
→ A의 논리적 스택과 상태를 유지하고 unmount
→ 빈 캐리어 P1이 가상 스레드 B 실행
→ A의 I/O가 끝나면 빈 캐리어에 다시 mount되어 재개
```

가상 스레드의 스택은 큰 OS 스택을 하나씩 영구 점유하지 않고 Java 힙의 stack chunk 객체로 유지·확장될 수 있다. 캐리어는 가상 스레드마다 새로 생기는 것이 아니라 JVM이 재사용하는 플랫폼 스레드다.

```text
플랫폼 스레드 → 보통 OS 스레드와 1:1, 비싸므로 풀에서 재사용
가상 스레드   → 작업마다 생성·종료, 여러 개가 소수 캐리어를 번갈아 사용
```

가상 스레드는 I/O 자체를 빠르게 하지 않는다. 대기 중인 작업이 OS 스레드를 붙잡지 않게 해 동시 처리량을 늘린다. DB 커넥션 수나 외부 API 한도 같은 진짜 희소 자원은 커넥션 풀·세마포어·Rate Limit 등으로 별도 제한해야 한다.

Java가 전부 가상 스레드로 바뀐 것도 아니다. 플랫폼 스레드와 가상 스레드는 함께 존재하고, 지원되는 Spring Boot 버전에서는 Java 21+와 `spring.threads.virtual.enabled=true`로 명시적으로 활성화한다.

## 한 문장 봉인

> 스레드는 프로세스 안의 독립 실행 흐름이라 각자 PC·레지스터 상태·스택을 가지며, 플랫폼 스레드는 OS 스레드와 보통 1:1로 대응해 풀에서 재사용된다. 가상 스레드는 I/O 대기 동안 캐리어 플랫폼 스레드를 놓아주어 소수의 OS 스레드로 많은 동시 작업을 표현한다.

## 학습법 회고

- 스레드 구조를 먼저 나열했을 때 “왜 필요한지 몰라 이해하기 어렵다”는 피드백이 나왔다. `대량 I/O 대기 → OS 스레드가 묶임 → 새 요청을 실행할 자리가 부족함`이라는 문제부터 다시 시작하자 가상 스레드와 캐리어가 연결됐다.
- 이는 새 규칙을 추가할 장면이라기보다 기존의 **원인·목적을 먼저 세운 뒤 구조를 설명한다**는 학습 성향을 지키지 못한 사례다. 다음 개념에서는 구조 이름보다 해결하려는 병목을 먼저 제시한다.
- 스레드 풀을 “플랫폼 스레드는 비싸므로 죽이지 않고 재사용하는 장치”로 연결했을 때, #09 ThreadLocal 정리와 Tomcat 요청 처리 흐름도 함께 재방문됐다.
